# 19. Decisions

## 19.1 Settled

System decisions only. Concert-specific choices and their deadlines are in `context.md` §6.

| # | Question | Decision |
|---|---|---|
| 1 | Guests without an email | Acceptable. The player receives their PDFs and forwards them. Guest email is optional on the player form. |
| 2 | Base quota variance | Uniform across players within a segment. Set at segment level; a per-player override column exists but is not surfaced prominently. |
| 3 | Do players attend their own show? | No. A player consumes zero seats in the player segment of their own show. |
| 4 | Extras policy | **Batch review** is the default for player segments. Requests hold as `PENDING_REVIEW`; admin grants after the deadline from a strict-FCFS preselected list. Public segments default to `AUTO_FCFS`. |
| 5 | **Mixed-mode shows** | Player-invited and public audiences **coexist in one show**. `audience_mode` lives on `show_segments`, not on the show; each segment owns its capacity, quota, deadline, policy and form. The show owns the hall. |
| 6 | Note visibility | Per-player grouping is **always admin-only**. The public wall is configurable per concert, and publishing to it is always an explicit admin action. |
| 7 | Retention | Keep indefinitely. No purge job. Soft deletes only. **Reversed by 46 (V3):** Trash with restore, and permanent delete from it. |
| 8 | Ticket vs portal | The PDF is the ticket; the portal is additive and decoupled. Content unlocks on admission, with a friendly pre-admission status page and a one-click `OPEN_TO_ALL` fallback. |
| 9 | Registration capture | Google Forms exports are a first-class input via import (`import.md` §9), equal to native forms. Neither is privileged in the data model. |
| 10 | Ticket editor | A real canvas editor over the organisation's own artwork, with seeded defaults so the system works before anyone opens it. |
| 11 | Database / auth / storage | **Supabase**, with a daily keep-alive cron defeating the 7-day idle pause. One service for three concerns; the pause is a solved problem, not a disqualifier. |
| 12 | Email transport | **Gmail SMTP via `nodemailer` from a Vercel Node.js function.** Only port 25 is blocked on serverless — 465 and 587 work. Behind a `MailTransport` interface so an HTTP provider is an adapter swap. |
| 13 | Booklet delivery | Supabase Storage with range requests; move the booklet alone to R2 only if egress demands it (`platform.md` §17.2). |
| 14 | Reference material | `ref.md`, not a vendored clone of Hi.Events. |
| 15 | Backend placement | Next.js Route Handlers and Server Actions. **No Supabase Edge Functions** — `sharp` cannot run on Deno, so rendering must be on Vercel anyway (`platform.md` §16.1). `claim_seats()` stays a Postgres function because it needs a row lock. |
| 16 | Repeat blasts | Idempotent by construction: `ticket_sent_at` as dedup key, a filtered `insert … on conflict do nothing`, and a partial unique index on pending outbox rows (`email.md` §11.4). |
| 17 | Base oversubscription | Always blocked, across all three mutations that can cause it. **No opt-out toggle** — lowering the quota or raising capacity already expresses the same intent honestly (`allocation.md` §7.4). **Reversed by 47 (V3):** an admin may exceed capacity or quota with a confirmation showing the overage. |
| 18 | Configuration | No operational value has a code default. Concert data lives in `context.md` and is entered through the admin UI (`README.md` §2.1, `domain.md` §6). |
| 19 | Admin accounts | **One shared `ADMIN` account** unlocked by a single secret code. No admin user management. Costs audit attribution, which is accepted; the schema still supports individual admins if that changes (`admin.md` §14.3). **Reversed by 50 (V3):** named accounts with `ADMIN`, `VIEWER` and `OPERATOR` roles. |
| 20 | Operator accounts | **Multi-account, provisioned by the admin, scoped to assigned shows** via `operator_show_assignments`. Enforced in the handler and again **in the database** — the manifest endpoint is the boundary that matters, since the manifest is the attendee roster (`checkin.md` §12.3). The database layer is a `security definer` function, not an RLS policy; see 20b, which amends this row. |
| 20a | Operator credentials | Supabase Auth password sign-in against a synthetic `<slug>@operators.invalid` address. **Not** anonymous sign-in and not a hand-rolled id/password pair — both move the credential check into our code, which is the thing the platform is there to do (`checkin.md` §12.1). |
| 20b | **How the database layer is enforced** | A **`security definer` function** — `manifest_for_show()` — reached by `supabase-js` `.rpc()`, with `execute` granted to `authenticated` and **no table grants at all**. Decided 4–5 Sep; it replaces the wording "and again by RLS" in 20. Two alternatives were measured and rejected. **Not RLS policies on the base tables**: PostgREST can only read a table `authenticated` has been *granted*, and that grant publishes the roster at `https://<ref>.supabase.co/rest/v1/attendees` to anyone holding the publishable key, which ships in the browser bundle by design — one layer on a newly opened door, where a policy bug is exploitable from a browser console. **Not a non-owner role plus `set local app.user_id`**: it is the textbook answer and does cover paths nobody has written yet, but 15 days out it changes `DATABASE_URL` in Vercel, CI and every `.env.local`, and makes every protected read run inside a transaction that sets identity first — a rule whose failure mode is a wrapper that forgets. Revisit after the concert. The cost of what was chosen is stated honestly: **coverage is opt-in**, so it protects only reads that call it — closed mechanically by an ESLint `no-restricted-imports` rule and `tests/auth/manifest-call-site.test.ts`, not by documentation. **Scope: the manifest read only.** Scan writes and the offline-sync drain stay handler-only — a scan write is a single row in an append-only, revertible log keyed by a token the operator physically holds, and its failure mode is a bad row, not the disclosure of the whole roster. RLS is additionally *enabled with no policies* on **every** table in `public`, so the deny is real if a grant ever leaks (`drizzle/0003_manifest_rls.sql`, `drizzle/0004_lock_down_public_grants.sql`). **Corrected 5 Sep, on first contact with the real project:** the argument above assumed the base-table grant was something a future diff might add. It was already there — Supabase pre-grants `anon` and `authenticated` every privilege on every table in `public` the moment the schema lands, 294 rows, and relies on RLS alone. Worse and separate, `execute` on a function defaults to `PUBLIC`, which both roles inherit, so every function was live at `/rest/v1/rpc/<name>` including `claim_seats()`. The decision stands and is now better supported: `0004` revokes the tables, sequences and functions, takes function `execute` off `PUBLIC` itself, revokes the default privileges, and enables RLS everywhere. Verified from outside with the publishable key and with a real signed-in session (`../local.md` §5a). |
| 21 | Capacity model | **One number per show** plus per-segment slices. No soft threshold, no `held_seats` column — held seats are simply seats no segment holds (`domain.md` §5.1, `allocation.md` §7.2). |
| 22 | Email addressing | Every message is addressed to a **registration**, never a seat. `email_outbox.registration_id` is the dedup key; a successful send stamps every attendee whose PDF it carried (`email.md` §11.4). **Extended, not narrowed, by V2's `player_notes_digest`** — the one message addressed to a player, who has no registration. `registration_id` became nullable to hold it, and the guarantee was kept by adding a *disjoint second key* rather than swapping the first: nullable `player_id`, a `check` that exactly one of the two is non-null, and a second partial unique index over the same pending statuses. A seat is still never an addressee, and without that check a row addressed to nobody would conflict with nothing and double-send silently (`domain.md` §5.1, `modules-v2.md` §3.1). |
| 23 | Review before send | Outbox rows are rendered into `DRAFT` and edited by a human — per template or per message — before anything is queued. The dispatcher sends stored content verbatim (`email.md` §11.5). **Narrowed by decision 38** for the feedback email only. **Narrowed again by 48 (V3):** review happens inside the Send tickets wizard. |
| 24 | Delivery outside the system | An explicit "Mark as delivered" admin action sets `ticket_sent_at` with `source = MANUAL`, so hand-delivered tickets leave the pending bucket (`email.md` §11.6). |
| 25 | Editing a response | May correct or reduce, never add seats. More seats means a new EXTRA request at the back of the FCFS queue (`v2.md` §8.3.1). |
| 26 | Import direction | One import run per segment; after commit this database is the source of truth and there is no rollback or re-sync (`import.md` §9.1). **Amended by 49 (V3):** a batch can be undone as a command, and rows are staged and committed in passes. |
| 27 | Referential integrity | Composite foreign keys, not triggers: an attendee cannot disagree with its registration about segment or show (`domain.md` §5.2). |
| 28 | QR durability | The scanner treats the QR as opaque data and never dereferences it, so a changed or dead `APP_URL` cannot affect admission. `qr_token` is immutable for life (`tickets.md` §10.1). **Narrowed by 55 (V3):** one explicit, audited command, *Void and re-issue QR*, may replace a token. |
| 30 | QR origin | **No custom domain.** The Vercel production alias `<project>.vercel.app` is the origin, which is safe because decision 28 makes admission independent of it. The project name is frozen before the first render and `APP_URL` is never derived from `VERCEL_URL` (`tickets.md` §10.1). |
| 31 | Party tickets | A registration is a party of N in both audiences: one email, N `qr_token`s, N PDFs. No shared "admits 4" QR. The door gets an **Admit remaining** control instead (`v2.md` §8.1, `checkin.md` §12.1). |
| 32 | Missing attendee names | Never blocking. Imported seats with no name ticket as "Guest of {contact_name}" with `name_source = PLACEHOLDER` (`v2.md` §8.2.1). |
| 33 | **Import takes a normalized sheet** | The admin reshapes a wide Google Form export into **one attendee per row** in the spreadsheet; the importer does column mapping only (`import.md` §9.2). The rejected alternative was a repeating-group mapper that unpivots wide→long in the UI, with header auto-detection proposing guest groups. It was the largest part of module `C` and all of its silent-failure surface — an `include_registrant_as_attendee` set wrong under-issues one ticket per party and is noticed only when someone reaches the door with nothing — for a reshaping step that a spreadsheet formula does in a minute, on ~100 registrations, in the tool the file already lives in. **The cost is that a long sheet has thrown away which rows are one party**, and a registration is a party of N by decision 31, addressed as one email by decision 22. So the importer rebuilds it: rows sharing `contact_email` **and** `requested_at` form one registration, a mapped `group_key` column overrides that, and the dry run reports the derived grouping before commit. Email alone would merge a person’s two rounds into one oversized party; the timestamp is what separates them. **Reversed by 49 (V3):** grouping by email within the segment, timestamp optional, wide sheets mapped in an editable staging grid. |
| 34 | **Editor scope in V1** | The canvas editor ships **upload a background, place and individually move and resize text, variable, QR, image and shape elements, versioned save, and the two previews**. §10.3 also lists snap-to-grid, alignment guides, lock, element duplicate, multi-select and undo/redo: those are **deliberately not in V1**, at the organisers' direction. Each is a feature rather than a polish pass, the artwork has to be laid out before 13 Sep, and none of them is needed to place a name over artwork. Recorded here because a QA pass correctly read their absence as a spec violation with nothing to point at (`tickets.md` §10.3). |
| 35 | **Form field mapping** | There is none. A block's destination is chosen when the block is created, not mapped afterwards: system blocks are pre-built from `registration_forms.kind` and their key fields are locked, and everything an admin adds is a custom field that cannot reach a column (`v2.md` §8.2). The rejected alternative was a free-form Google-Forms-style builder plus a "which field means the email?" mapping screen — the same machine decision 33 cut from module `C`, whose failure mode is silent and lands as a person at a door with nothing. |
| 36 | **The public registrant is seat #1** | On a public form the "Your details" block produces both the registration's contact fields and the first attendee, so the additional-seats repeater renders `form.max_tickets_per_response − 1` rows. The cap stays **total party size**, as `domain.md` §6 always defined it; configuring "extra guests" instead would make party size `cap + 1` on the capacity screens, in the import validator and at the door (`v2.md` §8.1.2). |
| 37 | **Conditional logic is custom-only** | A show/hide condition may only read from, and only target, a **custom** field. A system field is never either. A rule that could hide the email question or a seat's name would put the allocation path under something assembled in a UI, and the failure would be silent — the form would simply not ask (`v2.md` §8.2.2). |
| 38 | **Feedback email skips the `DRAFT` gate** | Marking a show `COMPLETED` queues feedback rows directly as `QUEUED`, **narrowing decision 23**. Defensible because the message carries no attachment, no per-person merge beyond a name and a link, and nothing irreplaceable. The real review window is the gap between queueing at ~10:30pm and sending at `portal.feedback_send_hour` — longer than the `DRAFT` gate gives in practice, and it also stops anyone being emailed at 10:30pm (`v2.md` §13.5.2). |
| 39 | **`COMPLETED` never closes the portal** | The two were briefly conflated and they contradict: `CLOSED` means status page only, so auto-flipping it on completion would take the feedback form down at the moment every attendee is emailed a link to it, and the booklet with it. `portal.unlock_mode` governs **who** sees unlocked sections and nothing else; each section ends on its own lifecycle (`booklets.published`, `portal.notes_close_at`, `portal.feedback_close_at`) (`v2.md` §13.2.1). |
| 40 | **"The show is over" is read from the clock** | The portal's post-show phase derives from `ends_at + show.auto_complete_after_hours` on read, so it is correct the instant it is true and needs no scheduled job — a guest opening their link at 11pm gets the feedback form. Only the `COMPLETED` flag and the email wait for the daily cron, and neither is visible to a human. This is why no hourly job was added: Vercel Hobby's two crons are spent (`platform.md` §17.1) and the precision buys nothing (`v2.md` §13.2.1). |
| 41 | **`ends_at` is required, never inferred** | With `shows.ends_at` null there is no post-show phase and no auto-completion, and an admin marks the show complete by hand. Inferring a duration from `starts_at` would flip a long concert into "how was your evening?" mid-performance; §2.1 already says a missing operational value is a validation error, not a silent fallback (`domain.md` §5.1). |
| 42 | **Every automatic step keeps a manual twin** | Auto-completion, feedback queueing, the timed send and the portal phase each have an admin control that does the same thing immediately — status dialog, **Generate feedback emails**, **Send now**, `OPEN_TO_ALL`. This is §2.4 applied to V2 rather than a new rule: automation that cannot be driven by hand fails on the one night nobody can wait for it (`v2.md` §13.5.3). |
| 43 | **No form level in the cascade** | `form.max_tickets_per_response` stays a **segment** value (`domain.md` §6) and `registration_forms.max_tickets_per_response` is vestigial: the form editor resolves and displays the cap read-only and never writes the column. The rejected alternative was a fifth cascade level below the segment, which `README.md` §2.2 calls authoritative — a change to `resolve_setting()`, to the wording of §2.2 and §6, and to every screen that explains the cascade. Its one real motivation is that a second round is a new form on the same segment, so two rounds could not differ in their cap; that does not survive contact with what a round is, because rounds do not overlap and caps resolve live, so changing the segment's value between them is both possible and free — a closed form renders nothing for the old value to be wrong for. Settled by `L`, which owns the screen that would have edited it (`v2.md` §8.3). |
| 44 | **Editing a note clears both flags, not just moderation** | §13.4 says editing an approved note returns it to `PENDING`, "otherwise moderation reviews one text and the wall publishes another". Resetting `moderation_status` alone does not achieve that: a note already `PUBLISHED` and then edited puts unreviewed text in front of the audience *immediately*, which is worse than the case the sentence was written for. So an edit also sets `wall_status` back to `NOT_PUBLISHED` and clears `moderated_by` / `moderated_at` — leaving them would credit an admin with approving words they never read. The two flags remain independent as admin controls (§13.4); this is one edit invalidating two reviews of a text that no longer exists. Settled by `O` (`v2.md` §13.4). |
| 45 | **A note addressed to a player can never be published** | §13.4 calls an addressed note personal mail bound for that player's digest, and §14.2 calls unaddressed notes "the natural public-wall candidates". `O` reads that as a prohibition rather than a preference: publishing someone's personal message to a player is a privacy decision its writer never made, and alone among this screen's mistakes it cannot be undone — a guest who has read it has read it. The publish action therefore **refuses the whole call** when the selection contains one, rather than publishing the rest and reporting the remainder; a partial success an admin skims past is how the wrong note ends up public. `lib/portal/wall.ts` filters addressed notes again on read, as belt to that braces. Loosening this later is a settings change; tightening it after a note has been read is not. Settled by `O` (`v2.md` §13.4, `admin.md` §14.2). |
| 29 | Delivery split | **V1** runs the concert (import → ticket → blast → door). **V2** adds native forms, the full portal and notes (`README.md` §4). |

## 19.3 Settled for V3

Decided with the owner on 24–25 Sep 2026, after the 19 Sep concert. Behaviour is in `v3.md`; the
blueprint they came from is linked there.

| # | Question | Decision |
|---|---|---|
| 46 | **Deleting** | Soft delete into a concert-scoped **Trash** with restore, plus **Delete permanently** from the Trash behind a typed confirmation. Reverses 7: "full access" was asked for explicitly, and a data-removal request needs a real delete (`v3.md` §23.6). |
| 47 | **Over capacity** | An admin may grant past a segment's capacity or a player's base quota. `claim_seats()` / `promote_seats()` take an explicit override parameter, the preview shows the overage, and the seat is flagged `OVER_CAPACITY`. Forms and imports never pass it. Reverses 17 (`v3.md` §23.5). |
| 48 | **Where review happens** | Inside a four-step **Send tickets** wizard — who, ticket design, email template, send — defaulted from the segment. Bulk sends always pass it; a one-party resend may skip the design and email steps. Replaces the separate draft screen; narrows 23 (`v3.md` §24.1). |
| 49 | **Import** | Rows land in an editable **staging grid**; ready rows commit in passes; timestamp optional; parties group by **email within the segment**; wide guest columns may be mapped because every derived row is visible and editable before commit; a batch can be undone. Reverses 33, amends 26. Decision 33's worry — silent under-issue from a wide mapper — is answered by the grid, not by forbidding the mapping (`v3.md` §25.7). |
| 50 | **Accounts** | Named accounts, three roles: `ADMIN`, `VIEWER` (read-only, masked contact details, no export), `OPERATOR`. No permission matrix. Reverses 19; the audit log now says who (`v3.md` §28). |
| 51 | **Unit of work** | The **party** is the record every screen opens and every command targets. Its stage and flags are **derived** by the `party_pipeline` view and never stored (`v3.md` §20.1, §21). |
| 52 | **Pending-message key** | One pending message per party per **purpose**, not per template; a redraft supersedes. Stricter than 16 and 22 — switching template can no longer send twice (`v3.md` §24.2). |
| 53 | **Registration links** | One public link per registration form, player forms included; a player form picks the inviting player from the roster. Personal invite links stay as an optional shortcut. Safe because every party passes the review gate (`v3.md` §25.1–§25.2). |
| 54 | **Receipt and review** | A receipt goes out automatically after submit, held briefly so repeat submissions collapse into one email, skipping `DRAFT` like the feedback email (38). Seats are claimed on submit; the party then waits for approval before it can be ticketed; duplicates across players and addresses are detected and merged (`v3.md` §25.3–§25.5). |
| 55 | **Void a ticket** | *Void and re-issue QR* is the one command that may replace a `qr_token` — explicit, audited, warning that printed copies stop working. Narrows 28 (`v3.md` §23.4). |
| 56 | **Inbox** | IMAP with the existing Gmail app password, not the Gmail API — which needs an OAuth app whose sign-in expires weekly in testing. Only mail matching a system-sent message is stored; bounces mark the message and flag the party (`v3.md` §26). |
| 57 | **Scheduler** | Supabase `pg_cron` + `pg_net` call one tick route every few minutes. Free on every plan and independent of repository activity, which rules out GitHub Actions for a public repo that stops receiving commits (scheduled workflows are disabled after 60 days without activity). The daily Vercel cron and the console's own loop remain as fallbacks (`v3.md` §27). |
