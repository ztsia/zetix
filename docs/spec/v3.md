# V3 — one pipeline around one record

*The admin console rebuilt around the party: derived stages, work queues, whole-job commands, an inbox,
full admin access, roles, and a scheduler. **Specified, not built.***

Part of the system specification — see [`README.md`](README.md) for the index, and
[`decisions.md`](decisions.md) §19.3 for the decisions V3 settles and the ones it reverses.

**Built by:** `P`–`X`. See [`../modules-v3.md`](../modules-v3.md) for what each label owns and in what
order.

The blueprint this was written from — inventory, diagrams, mock-ups — is published at
<https://claude.ai/artifact/SQTgELsH3a7Vcq9F26s1RL>. Where it and this file disagree, **this file wins**.

## 20. Why V3 exists

V1 and V2 were built as fifteen modules (`A`–`O`) by parallel sessions, one table and one screen each.
Every feature works. The console does not: each screen shows **one step for every party**, none shows
**every step for one party**, and none says what to do next. Getting a party its tickets took three
screens — Tickets (issue), Email (segment, template, prepare, review, confirm, send), and an unlinked
`/email/delivery` page to repair anything — and a bounced address took SQL.

Four findings drive every section below:

1. **A party's state is spread over six places** — `registrations.status`, `attendees.status`,
   `attendees.qr_token`/`ticket_issued_at`, `email_outbox`, `attendees.ticket_sent_at`, `check_ins` —
   and no query combines them into "where is this party?".
2. **Copies go stale.** `email_outbox.to_email` is copied at draft time and the dispatcher sends the
   copy, so fixing an address on the registration never reaches a drafted or queued message.
3. **The pending-message index is per template.** A redraft under a different template does not
   replace the first draft, so both send.
4. **Guardrails built for a rushed first concert now block repairs.** Edits only in `DRAFT`, no cancel
   once `QUEUED`, exhausted `FAILED` rows stuck forever, few deletes.

### 20.1 Principles

These are requirements, in the same sense as `README.md` §2.

1. **The party is the unit of work.** A registration is already the unit of email (decision 22) and of
   a form response. Every operational action starts from a party or a selection of parties.
2. **Status is derived, never stored.** A party's stage and flags are computed from facts that already
   exist (§21). Nothing new is written to record "where a party is", so it cannot drift from the
   facts.
3. **Queues are filters, not screens.** A work queue is a saved filter over one table (§22.2).
4. **Commands finish the job and are safe to repeat.** A command previews what it will do, runs, and
   reports per row. Running it again does only what is left (§23).
5. **The system never refuses the admin; it explains.** Every record is editable, every status is
   settable, everything is deletable. Destructive commands state their real consequences first
   (§23.3). What remains enforced protects data integrity, not policy (§23.4).
6. **Nothing operational is hardcoded** — unchanged from `README.md` §2.1. Every new tunable in this
   file is a settings key (§30.2).

## 21. The party pipeline

### 21.1 Stages

A party's stage is **the first step it has not finished**, computed per party by the database view
`party_pipeline` (§30.1). Seats that are `CANCELLED` or soft-deleted are ignored; a party with no live
seats is off the line.

| Stage | A party is here when | Next action |
|---|---|---|
| `NEEDS_REVIEW` | It has not been approved (§25.4), **or** it has seats `PENDING_REVIEW` (extras awaiting a first-come decision) | Approve / grant or decline |
| `UNVERIFIED` | Public party whose `email_verified_at` is null and no admin release | Remind or release |
| `NEEDS_TICKETS` | A `CONFIRMED` seat has no issued ticket | Send tickets (§24) |
| `READY_TO_SEND` | Every confirmed seat is issued; at least one is not delivered | Send tickets (§24) |
| `SENT` | Every confirmed seat is delivered, by email or by hand | — |
| `ADMITTED` | Every confirmed seat is delivered, and at least one seat has a live check-in | Feedback (after the show) |

`ADMITTED` is the last step, so it is reached only once every earlier step is finished: a party with
one guest inside and a second seat still unticketed is `NEEDS_TICKETS`, because that seat is the work.

Two states sit beside the line:

- **`WAITLISTED`** — no confirmed seats, at least one `WAITLIST`. It moves forward when seats are freed
  and promoted.
- **`CANCELLED`** — every seat cancelled. Restorable (`allocation.md` §7.9).

The view also returns the rollup counters every screen needs: confirmed, pending, waitlisted,
issued, delivered and admitted seat counts, so "2 of 3 sent" is read, never recomputed in TypeScript.

### 21.2 Flags

A flag is a problem a person has to look at. Flags overlay any stage and are computed by the same view.

| Flag | Raised when |
|---|---|
| `BOUNCED` | The latest ticket-bearing message (`TICKETS`, or a granted `EXTRAS_DECISION`) to the current address bounced (§26.4) |
| `SEND_FAILED` | A message exhausted `email.max_attempts`, and nothing of its purpose was sent after it — nor, for a ticket-bearing one, did every ticket reach the party another way |
| `SUSPICIOUS_ADDRESS` | The contact address fails the syntax, typo or MX check (§24.6) |
| `CHANGED_AFTER_SEND` | Any seat has `needs_reissue` (`tickets.md` §10.6) |
| `POSSIBLE_DUPLICATE` | An open duplicate candidate names this party, and the other party is still live (§25.5) |
| `UNNAMED_GUESTS` | A seat has `name_source = PLACEHOLDER` |
| `REPLY_WAITING` | The newest message in its thread is inbound and unhandled (§26.5) |
| `OVER_CAPACITY` | A seat was granted by an admin over capacity or quota (§23.5) |

Stage answers "what is next"; flags answer "what is wrong". Home counts both (§29.2).

### 21.3 Seat-level request time

Merging parties (§25.5, and import grouping by email, §25.7) must not let a late seat jump the
first-come queue. So **each seat carries its own `attendees.requested_at`**, set from the submission or
import row that created it. `registrations.requested_at` stays as the party's earliest seat and remains
the ordering key for party-level screens; the extras walk (`allocation.md` §7.5) orders by the seat's
own time.

## 22. The Audience workspace

### 22.1 One table, two grains

`/admin/concerts/{id}/audience` is one server-paged `DataTable` over `party_pipeline`, with a
**Parties / Seats** toggle. The seat grain carries the ticket columns today's Tickets screen has. Both
grains share one filter model, so a queue means the same thing in either.

It **replaces** as separate screens: Registrations, Unverified, Extras review, Tickets, and
Email › Delivery. Their behaviour survives as views, commands and record actions.

### 22.2 Saved views

A view is a named filter, encoded in the URL so it can be linked. Built-in views, one per stage and one
per flag, each with its count: *Needs review, Unverified, Needs tickets, Ready to send, Sent, Admitted,
Waitlisted, Cancelled, Bounced, Send failed, Suspicious address, Changed after send, Possible
duplicates, Unnamed guests, Replies*. The admin can save their own.

**Needs review keeps the extras pool meter** of today's review board — the live "N seats left in the
pool" counter that makes the first-come walk possible — as the view's toolbar.

### 22.3 Selection is a query, not a page

Every table in the console selects the same way (a shared `DataTable` capability, `P`/`Q`):

- Ticking rows selects those ids.
- **"Select all N matching"** selects the *filter*, across every page. The command receives
  `{ filter, excludedIds }`, never a client-assembled id list, and resolves it on the server inside the
  command's own transaction — so what runs is what matched at run time, and the preview says so.

This generalises the tickets screen's `matchingTicketIdsAction` (PR #46) to every table.

### 22.4 The party record

A row opens the record — a full page, not a sheet, because it is where the work is done.

- **Header:** contact name, email (inline edit with the §24.6 checks), phone, player, show and segment,
  source with provenance (form and round, or import batch and row number, or admin), stage badge and
  flags, the stage's next action as the primary button, and a menu holding every other command.
- **Seats:** per seat — name (editable), allocation type, status, ticket code, pinned template version,
  delivery state, check-in state. Per-seat actions: download PDF, reissue, void and re-issue (§23.4),
  cancel, check in manually, delete.
- **Conversation:** every message to and from this party in one thread, including bounces (§26), with
  a reply box.
- **Responses:** the form response and its edit chain, or the import row as it was in the file.
- **Activity:** this party's `audit_log` entries, newest first.

Editing the contact email when tickets have already been delivered asks one question — *"Tickets were
sent to the old address. Resend them to the new one?"* — and answering yes runs Send tickets (§24) for
this party with review optional (§24.3).

As built (`S`): the workspace is `src/app/(admin)/admin/concerts/[concertId]/audience/`, its reads are
`src/lib/audience/` (`filter.ts` is the one filter model; `queries.ts` pages both grains over
`party_pipeline`; `record.ts` loads the record). A view is the URL key `view` (`needs-review`,
`bounced`, …); the Seats grain adds `status` and `ticket`, which refine seats and never parties. The
four retired screens redirect to their view (`/registrations/unverified` → `?view=unverified`,
`/extras-review` → `?view=needs-review`, `/tickets` → `?grain=seats`); ticket designs stay at
`/tickets/templates` until `W` moves them under Setup. Until the send wizard exists, the record's
email edit re-addresses pending messages (§24.3), stores the §24.6 check, and *says* that tickets went
to the old address; the resend itself is `T`'s.

## 23. Commands

### 23.1 Shape

A command is a named server operation over a selection (§22.3). Every one has three phases:

1. **Preview** — the server resolves the selection and returns what will happen to each row, which rows
   will be skipped **and why**, and the blast radius (§23.3). Nothing is written.
2. **Run** — the command executes as a `command_run` with one `command_run_items` row per target
   (§30.1). Small runs complete in the request; runs that would outlive `maxDuration` continue from the
   scheduler tick (§27).
3. **Report** — per-row outcome. Failures land in the relevant flag queue. The run is kept and readable
   from the Activity log.

**Idempotent by construction.** A command re-run over the same selection does only what is left; this
is how partial progress converges without anyone untangling it.

### 23.2 The command set

| Area | Commands |
|---|---|
| Review | Approve · Grant extras · Decline extras · Merge parties · Not a duplicate |
| Allocation | Confirm seats · Waitlist · Promote from waitlist · Move to segment · Cancel · Restore |
| Verification | Release (treat as verified) · Send verification reminder |
| Tickets | Issue · Reissue · Void and re-issue QR · Dismiss reissue flag |
| Delivery | Send tickets (§24) · Resend · Mark delivered by hand · Cancel sending |
| Messages | Retry · Cancel · Edit (any status before `SENT`) · Delete |
| Door | Check in · Undo check-in |
| Records | Edit field · Set status · Delete · Restore from Trash · Delete permanently |
| Intake | Undo import batch · Commit staged rows |

As built (`S`): Review, Allocation, Verification, Tickets, Door and Records are
`src/lib/audience/commands/` (`audience.*` over parties, `seats.*` over seats). Merge parties and Not
a duplicate are `V`'s; Delivery and Messages are `T`'s. Choices worth knowing:

- **Grant extras and Promote walk first come first**, ordered by each party's earliest seat of the
  kind being decided (§21.3), for hand-ticked ids as well as filters (the runner's `order` hook). Once
  a party does not fit, later parties of the same run in that segment are skipped, not granted past
  it; the override is the way past. With `allow_partial_grant` the boundary party takes what is left
  and the rest stay in review.
- **Send verification reminder queues** (`QUEUED`, not `DRAFT`): the command's preview is the human
  review decision 23 asks for.
- **Check address / Accept address** (Records) run and override the §24.6 check per party, which is how
  parties from before V3 get checked at all.
- **Void and re-issue QR** replaces the ticket code with the token, so a manual lookup of the old
  printout finds nothing, and puts a delivered seat back in Ready to send. `0202` lets it past
  `tg_qr_token_immutable()` under a transaction-local flag; nothing else gets past. It is the one
  command a re-run does not skip: voiding again is a new decision (a second leak), so it replaces the
  token again, behind the same typed confirmation.
- **Pending ticket mail follows the seats.** Waitlist, Set status and Delete seat withdraw a party's
  `DRAFT` / `QUEUED` ticket-bearing messages once it holds no confirmed seat, as Cancel always has
  (`allocation.md` §7.9); clearing a contact email withdraws its pending messages rather than leaving
  them addressed to the old one.

### 23.3 Blast radius

Every destructive or state-reversing command's preview states its consequences, **counted from real
data**, in the terms a guest would notice:

> Delete 3 parties — 7 seats, **4 tickets already delivered** (their QR codes will be refused at the
> door), 1 check-in, 9 messages kept in history.

A typed confirmation phrase is required only when a command is both **irreversible** and **large**;
the threshold is `admin.typed_confirm_above` (§30.2). Every command takes an optional reason, written
to `audit_log.reason`.

The phrase is the command's verb, the count of rows that will run and the noun: *delete permanently
34 parties*. It is checked against the count **at run time**, so a filter selection that grew after
the preview no longer matches what was typed and the admin is sent back to preview. "Large" means more
rows than the threshold; a threshold nobody has set requires the phrase.

As built (`Q`): the runner is `src/lib/commands/`, every command is one definition registered in
`registry.ts`, and every screen reaches them through the same five Server Actions and one dialog. A
run works one row per transaction, re-reading each row under a lock as its turn comes, which is what
makes a re-run do only what is left. A run that outlives one request is continued by the open
dialog, or by the tick through `continueRegisteredRuns()`.

### 23.4 What stays enforced

These protect the data's integrity rather than restrict the admin, and no command bypasses them:

- **Seat counts stay true.** Every seat mutation goes through `claim_seats()` / `promote_seats()`.
  Going over capacity is an explicit parameter to those functions (§23.5), not a bypass of them.
- **Nothing double-sends.** One pending message per party per **purpose** (§24.2).
- **A QR never changes silently.** `qr_token` is still immutable under every command except **Void and
  re-issue QR**, which is explicit, audited, and warns that any copy already printed stops working. It
  exists for a leaked or disputed ticket. This narrows decision 28 by exactly one named command (decision 55).
- **A seat cannot disagree with its party** about show or segment (composite FKs, decision 27).
- **The scanner still never dereferences the QR** (decision 28).

### 23.5 Over capacity and quota

`claim_seats()` and `promote_seats()` already take `p_override boolean default false` — since V1 it has
relaxed the segment and hall ceilings and nothing else (`allocation.md` §7.8). With it false — every
public form, every import, every command without the override — behaviour is exactly
`allocation.md` §7.4, including the base-oversubscription guard. With it true, V3 lets the grant proceed
past the player's base quota as well, the seat is flagged `OVER_CAPACITY` (§21.2), and the preview has
already shown the overage ("this puts the Public segment at 312 of 300"). **Reverses decision 17**
(decision 47).

A seat is marked (`attendees.over_capacity_at`) only when the override was actually **needed** for it —
past the quota, the segment or the hall. A seat that would have been granted anyway is not marked, and
nor is one that only went past the extras pool: the pool sizes a recommendation, not capacity. Only a
quota that exists can be exceeded, so a BASE request from a party linked to no player still waitlists;
the lever for such a party is `COMP`. Both functions return the count as `over_capacity`.

### 23.6 Trash

Deletion stays soft (`deleted_at`) and lands in a concert-scoped **Trash** that lists deleted parties,
seats, messages, forms, players and templates, each restorable. **Delete permanently** from the Trash
is a real `DELETE`, covered by §23.3's typed confirmation, and the audit row it leaves records what was
removed but not the personal data. **Reverses decision 7** (decision 46).

- **Restore re-decides seats.** A seat that was confirmed when it was deleted is offered back to
  `promote_seats()`, not simply undeleted (§23.4). If the room was given away, it comes back
  waitlisted, and the report says so with the engine's reason. A seat deleted with its party comes
  back with the party. A seat removed on its own stays in the Trash as a seat.
- **A single restored seat is decided like a new seat on its party.** Its earlier status is not
  kept. An extra in a `REVIEW` segment goes back to review. A seat whose party holds no confirmed seat
  waits with the party rather than jumping its queue. Otherwise the engine decides.
- **Delete permanently refuses, per row, where a cascade would damage something outside the Trash**:
  - a party or seat with a guest admitted at the door;
  - a form a live party registered through;
  - a player a live party is linked to;
  - a ticket design any ticket is pinned to;
  - a message being sent, or a party or player one is being sent to.

  Purging a party also deletes its form response and the edits it superseded, except any response
  another party's history also passes through.
- **Deleting permanently reaches the history.** Earlier Activity rows about the deleted rows (a
  party's rows cover its seats) keep what happened and when, but their `before` / `after` are replaced
  with a marker, and a restore report stops naming the row. Rows written in bulk with no entity id
  cannot be traced to a person and are left alone. The preview counts the rows it will redact.
- **A purged ticket's `ticket_code` can in principle be minted again.** Codes are random and the door
  admits by `qr_token`, never by code, so a reuse can mislead only a manual lookup of an old printed
  ticket. This is accepted rather than guarded by a register of retired codes.
- **Email templates are not in the Trash.** They are global, not per concert, and keyed by text. The
  module that first deletes one decides how they are restored.

## 24. Send tickets and messages

### 24.1 The wizard

**Send tickets** is one command (§23) presented as a four-step wizard over any selection:

1. **Who** — the selection resolved: how many parties will be sent, how many need tickets issued first
   (issued in the same run), and every skip with its reason (unverified, waitlisted, not approved, no
   address, suspicious address).
2. **Ticket design** — the design each segment will use, defaulted from the segment, with a real
   rendered PDF preview of the longest name in the selection. Changing it here pins the chosen design
   for these seats.
3. **Email** — the template, defaulted from purpose × audience (§24.2), previewed as any recipient in
   the selection. **Edit wording for this send** edits this run's drafts only, not the library template.
4. **Send** — review of the counts, then run.

The wizard **replaces** today's prepare → review → confirm → send screen, and it is where decision 23's
review happens: bulk sends always pass through it; a one-party resend from the record may skip steps 2–3
(`delivery.review_single_party`, §30.2). **Narrows decision 23** (decision 48).

### 24.2 Purposes

A message has a **purpose**; the template is only how that purpose is worded.

| Purpose | Default template (by audience) | Carries tickets |
|---|---|---|
| `RECEIPT` | `registration_receipt` (new, §25.3) | no |
| `VERIFICATION` | folded into `RECEIPT` for public forms; `public_verify` for reminders | no |
| `TICKETS` | `player_confirmation` (player) · `public_ticket` (public) | yes |
| `EXTRAS_DECISION` | `extras_granted` · `extras_declined` | granted: yes |
| `CANCELLATION` | `registration_cancelled` | no |
| `REMINDER` | `reminder` | no |
| `FEEDBACK` | `feedback_request` | no |
| `NOTES_DIGEST` | `player_notes_digest` (player-addressed) | no |
| `PLAYER_INVITE` | `player_invite` (new, §25.2) | no |
| `REPLY` | none — written by a person (§26.6) | no |

Each segment stores its default ticket design (`show_segments.default_ticket_template_id`, the segment
level of `ticket.default_template_id`'s cascade) and its default template per purpose
(`segment_message_defaults`; no row means the table above); the wizard reads them and the admin can
override per send.

**The pending-message rule moves from template to purpose.** `outbox_no_duplicate_pending` becomes
unique on `(registration_id, purpose)` over `DRAFT`, `QUEUED`, `SENDING`, and the player-addressed
index likewise (§30.1). **`REPLY` is outside both indexes**: two replies a person wrote are two
messages, and superseding the first would silently discard something a human composed. Drafting again for a purpose **supersedes** the pending draft — it is set
`CANCELLED` with `superseded_by_id` pointing at the new one — so switching template can never send
twice. This is stricter than decisions 16 and 22, not looser.

### 24.3 The recipient is resolved late

A pending message stores the address it will use, but **editing a party's contact email re-addresses
its pending messages** in the same transaction, and a message already `SENT` is never rewritten. The
record's resend question (§22.4) covers the sent case.

### 24.4 Every message has an exit

From the Messages view (`Audience › Messages`, all purposes, all statuses) and from the record:

| Status | Available |
|---|---|
| `DRAFT` | edit, cancel, delete |
| `QUEUED` | edit, cancel (back to `CANCELLED`), delete |
| `SENDING` | none — it is in flight; the dispatcher resolves it |
| `FAILED` | retry (resets attempts), edit address and retry, cancel, delete |
| `SENT` | view, resend (a new message), delete from history |
| `BOUNCED` | view, fix address and resend, delete |

`BOUNCED` is a new terminal status set by the inbox (§26.4).

### 24.5 Scope bug fixed by construction

The shell's queue banner reads the backlog **for the concert in view**, not table-wide
(`local.md` §14.1).

### 24.6 Addresses are checked everywhere they enter

The existing checks in `lib/email/address.ts` — syntax, the typo suggester (`gmail..com` →
`gmail.com`), and the MX lookup — run on every path an address enters: the public form (as today),
import staging (§25.7), the record's inline edit, and the wizard's Who step. A failing address raises
`SUSPICIOUS_ADDRESS` and is skipped by Send tickets until fixed or overridden. The import's loose
pattern (`plan.ts` `EMAIL`), which accepts `gmail..com`, is replaced by the shared check.

## 25. Intake

### 25.1 One public link per form

Every registration form — player and public alike — has **one public URL**, `/f/{slug}`, with a Copy
link control for sharing on WhatsApp. Sending players email invitations is optional.

### 25.2 The player form without tokens

A player form identifies the inviting player by a **searchable picker over the active roster**, not by
`?k={invite_token}`. Remaining base seats are shown for the picked player. The picker is the
registrant's claim, not proof — which is exactly why every party passes the review gate (§25.4) and
why duplicate detection looks across players (§25.5).

`players.invite_token` stays, and `/f/{slug}?k={token}` keeps working as a prefilled shortcut for a
player who received the optional **Invite players** email (`PLAYER_INVITE`, §24.2). This supersedes the
Access row of `v2.md` §8.1 for player forms.

### 25.3 The receipt email

On submit, the form queues one `RECEIPT` message for the party:

- It states what was received (N seats, with names), that tickets follow once the organisers confirm,
  and to check the spam folder and add the sender to contacts.
- On a public form it **carries the verification link** — one email, not two. `public_verify` remains
  for reminders.
- It is **held** for `email.receipt_hold_minutes` (§30.2) before it becomes due. A second submission
  from the same address merges into the same party (§25.5) and, under the purpose rule (§24.2),
  **supersedes** the pending receipt — so one email covers every seat. A submission after the receipt
  has gone out sends an "updated" receipt, which is correct: something changed.
- It **skips the `DRAFT` gate**, as the feedback email does (decision 38), for the same reasons: no
  attachment, no irreplaceable content, and a person on the other end waiting to know it worked.

The form's thank-you page shows immediately, so the hold costs the registrant nothing. The hold ends
when the next scheduler tick sends it (§27). Import can queue receipts too, off by default per batch,
since Google Forms respondents already received Google's own confirmation.

### 25.4 The review gate

**Seats are claimed on submit** — capacity and first-come order stay real, exactly as today. The party
then carries `registrations.approved_at = null` and sits in `NEEDS_REVIEW` (§21.1), which **Send tickets
skips**. Approval is a command (§23.2):

- Parties with **no flags** can be approved in bulk from the view.
- `review.auto_approve_clean` (§30.2), when true, approves a party with no flags at submit.
- Imports land in the same queue.
- Admin-created parties are approved on creation.

Approval gates the ticket, never the seat — the same stance `v2.md` §8.1.4 takes for verification.

### 25.5 Duplicates and merging

A **duplicate candidate** is a pair of live parties in the same show that match on any of:

- the same contact email (case-folded — `citext` already does this),
- the same phone after normalisation,
- a contact or attendee name at or above `review.duplicate_name_similarity` (`pg_trgm`, already
  installed),

across players and across segments of the same show. Candidates are stored (`duplicate_candidates`,
§30.1) so a "Not a duplicate" decision sticks, and raise `POSSIBLE_DUPLICATE`.

**Merge** moves the seats of one party into another in one transaction — seats keep their own
`requested_at` (§21.3), the absorbed party is soft-deleted with a pointer to the survivor, its pending
messages are superseded, and its form responses re-point. Merge goes through `claim_seats()` when the
parties are in different segments, since that is a move.

**One party per email per segment is the default.** A native form submission from an address that
already holds a live party in the segment **adds to that party** rather than creating a second one,
subject to the party-size cap, which the admin may override. This is decision 25's "never add seats"
applied to the *edit link*, which is unchanged; a fresh submission is a new request, placed at the back
of the first-come queue by its own `requested_at`.

### 25.6 Forms on their parents

Each form is shown on its segment's (or show's) setup page as well as under Intake, with its funnel —
*responses → parties → approved → sent*. Per-form themes (banner image, colour taken from it, admin
override, contrast checked before use as button text) set `--form-*` tokens on the form wrapper and
nothing else; the banner lives in a **public** bucket, since `ticket-assets` is private
(`forms-google-layout` handoff).

New form behaviour, in priority order:

1. **Party update link** — a per-party tokenised link (the party's own `edit_token`, or a new one for
   imported parties) where the party names unnamed guests, corrects its email (re-verified), or
   **gives back seats**. Returned seats are cancelled and the waitlist is promoted.
2. **Waitlist mode** — when a segment is full, its public form takes waitlist requests instead of
   closing (`WAITLIST` seats already exist in the model).
3. **Player roster form** and **general survey** (no seats) — later, only if asked for.

Contact forms are out of scope: they start threads the system did not begin (§26.1).

### 25.7 Import becomes a staging grid

Upload → choose the target segment → map columns (profiles unchanged) → rows land in
`import_rows` (§30.1) — **an editable grid**, not a read-only dry-run report:

- Issues are shown on the cell. Editing a cell re-validates that row and its party at once.
- **Commit the rows that are ready.** Blocked rows stay staged for later; one bad row never blocks the
  run. The batch is committed in as many passes as it takes.
- **Timestamp is optional.** Without it, file order is the first-come order; it only matters for
  extras.
- **Grouping is by contact email within the segment** (decision 33 amended, decision 49). A mapped
  `group_key` still overrides. An email that already holds a party in the segment offers, per party:
  **add seats to it** (default), skip, or keep separate. Re-uploading the cumulative sheet each round
  therefore needs no timestamps to dedupe: an unchanged party is recognised as already imported by
  email and seat names.
- **Wide sheets are accepted.** Repeating column groups (`Guest 1 Name`, `Guest 2 Name`, …) can be
  mapped as a seat group, previewed as rows in the grid before commit — the grid is what makes this safe
  where decision 33 found it unsafe, because every derived row is visible and editable before it is
  written.
- **Undo import** is a command (§23.2) over everything a batch created, with its blast radius.

## 26. Inbox — the lite CRM

### 26.1 Scope

Only threads the system started. Replies are read from the record and answered from it; there is no
compose-to-anyone. Mail in the inbox that does not match a system message is never stored.

### 26.2 Outgoing messages are tagged

Every outgoing message carries:

- **Our own `Message-ID`**, `<{outbox_id}.{random}@{sender-domain}>`, stored on the outbox row.
- **A plus-addressed `Reply-To`**, `{local}+p{registration_id}@{domain}` (or `+pl{player_id}` for the
  player digest). Gmail delivers plus-addresses to the same inbox, and the tag survives mail clients
  that drop threading headers.

### 26.3 Sync

`MailInbox` is a new adapter interface beside `MailTransport` (decision 12's pattern, §26.7). The
first adapter is **IMAP** against the same Gmail account, authenticated with the existing
`GMAIL_APP_PASSWORD` — app passwords cover IMAP, and no Google OAuth app is needed.

Each sync reads messages with UIDs above the stored cursor (`mail_sync_state`, per folder), from
**INBOX** and **Sent Mail** (so a reply written in Gmail itself joins the thread), within a time budget
that fits `maxDuration`. It runs on every scheduler tick (§27), while the admin console is open, and
when a party record is opened.

### 26.4 Matching and bounces

A message is matched, in order, by `In-Reply-To`, then `References`, then the plus tag, then — for a
reply that lost all three — by sender address equal to a party's contact email **within 30 days of a
message to it** (`inbox.match_fallback_days`, §30.2). Unmatched mail is skipped.

A **delivery-status notification** (from `mailer-daemon@googlemail.com` and similar, `multipart/report`
or the message it quotes) is matched through the **original message's `Message-ID`** it carries. The
matched outbox row becomes `BOUNCED` with the diagnostic code and text stored, and the party is flagged
`BOUNCED` (§21.2). A `SENT` is therefore no longer read as "arrived" once a bounce is known
(`local.md` §13.1).

### 26.5 Threads

A thread is the party's conversation: its outbound messages, inbound replies and bounces, in order. An
inbound reply raises `REPLY_WAITING` until an admin replies or marks it handled. The Inbox area lists
open threads across the concert, newest first.

### 26.6 Replying

A reply is written on the record, stored as an outbox row with purpose `REPLY`, and sent at once
(no `DRAFT` gate — a person wrote it). It carries `In-Reply-To` and `References`, so it threads in the
guest's client and in Gmail's Sent folder.

### 26.7 Mail adapters stay liftable

`src/lib/mail/` holds `MailTransport`, `MailInbox`, the Gmail SMTP and IMAP adapters, and the test
adapters, and imports nothing from the rest of the app. That keeps a later extraction into its own
package a move, not a rewrite. Other providers (Microsoft Graph, Gmail API) are new adapters. Local
development uses **Mailpit** as the SMTP sink rather than a hand-built one.

## 27. Scheduled work

### 27.1 The tick

One route, `/api/scheduler/tick`, authenticated by a bearer secret, does in order within its time
budget: auto-complete shows (as today), send what is due (receipts past their hold, queued messages,
due feedback), continue unfinished command runs (§23.1), and sync the inbox (§26.3). It records
`scheduler_heartbeat` (§30.1).

### 27.2 What calls it

- **Supabase `pg_cron` + `pg_net`** call the route every `scheduler.tick_minutes` (§30.2). Both
  extensions are available on every Supabase plan; `pg_cron` is limited only by the database's own
  resources. The job is created by `schedule_scheduler_jobs()`, which reads the setting, and changing
  the setting re-schedules it (`cron.alter_job`, from a trigger on `system_settings` once the job
  exists). The tick URL and the secret are stored in **Supabase Vault** as `zetix_scheduler_tick_url` and
  `zetix_scheduler_secret` and read by the job each time it runs — never in a migration, never in
  `cron.job`.
- **A second `pg_cron` job trims `cron.job_run_details`** and `net._http_response` older than
  `scheduler.history_days`, since a job every few minutes grows them without limit.
- **Fallbacks:** the daily Vercel cron on `/api/outbox/dispatch` is repointed at the tick, and the
  admin console's own loop keeps sending while it is open.

`pg_cron` runs inside the database, so it cannot wake a paused project: the keep-alive crons stay.
Home shows the last heartbeat and warns when it is older than three ticks.

### 27.3 Local development

The local Postgres 16 has no `pg_cron`. The scheduling function is created only where the extension
exists, and tests call the tick route directly. Enabling the extensions and storing the secret are
manual steps (`local.md` §16).

## 28. Roles and accounts

**Named accounts with three roles**, replacing the one shared admin code (decision 50):

| Role | Can | Cannot |
|---|---|---|
| `ADMIN` | Everything, including provisioning accounts and roles | — |
| `VIEWER` | Read every admin screen | Run any command, export, or see full email addresses and phone numbers (shown masked) |
| `OPERATOR` | Unchanged — sign in, scan, search within assigned shows | Unchanged (`admin.md` §14.3) |

- Admin and viewer accounts sign in with email and password through Supabase Auth; an admin provisions
  them from **Settings › People**. The bootstrap script creates the first admin.
- `requireAdmin()` becomes `requireRole(...)`. Every Server Action and Route Handler re-checks its role,
  as every one re-checks `requireAdmin()` today, and the existing guard tests extend to viewer denial.
- `audit_log.actor_id` now names a person. The Activity log shows who.
- Login rate limiting is unchanged and applies per account as well as per IP.
- **Masking happens on the server**, before a page hands data to the browser; a mask applied in the
  browser is a mask over data the viewer already holds. It covers every email-shaped string and every
  phone field on every screen, including audit `before` / `after` and command reports. A viewer's
  search never matches a column they see masked: a row that appears for one guess and not the next
  spells the value out a character at a time. Where a screen's search runs on the server, a viewer
  searches names, labels and ids only.
- **A viewer holds no access token.** Ticket links (`/t/{token}`), ticket PDFs, player invite links and
  the like are withheld as well as addresses: whoever holds one can act as the attendee or player,
  which read-only rules out. A viewer is not admitted to the door scanner either.
- **Passwords are generated and shown once**, like an usher's code; an admin issues a new one from
  the person's row. There is no invitation mail and no self-service reset.
- **The console always keeps an active admin.** Demoting or deactivating the last one is refused, and
  nobody may demote or deactivate themselves. If every admin is locked out anyway, the bootstrap
  script restores one.

No custom permission matrix. A fourth role is a new enum value and a guard, not a framework.

### 30.1 One migration, `0200`

V3 starts migrations at `0200`, as V2 started at `0100`. Everything below is `P`'s single migration,
`drizzle/0200_v3_schema_delta.sql`.

- **`party_pipeline`** — a view returning, per live registration, the stage (§21.1), the flags (§21.2)

  `security_invoker`, and no grant to `anon` or `authenticated`.
- **`attendees.requested_at`** (§21.3), backfilled from the registration; a trigger fills it from the
  registration when an insert leaves it out, and `claim_seats()` takes an explicit one per seat.
  **`attendees.over_capacity_at`** (§23.5) and **`attendees.import_row_id`** (§25.7 — per seat, because
  an import can add seats to a party it did not create, and Undo must remove exactly those).
- **`registrations.approved_at`**, `approved_by` (§25.4); backfilled to `created_at` for every existing
  registration so nothing already ticketed goes back to review. **`merged_into_id`** (§25.5).
  **`update_token`** (§25.6 — the update link for a party with no form response to carry an
  `edit_token`). **`email_issue`**, `email_checked_at`, `email_issue_accepted_at` (§24.6 — the address
  checks run in the app, so their result is stored for the view to read as `SUSPICIOUS_ADDRESS`).
- **`email_outbox`**: `purpose` (enum, backfilled from `template_key`, **no default**), `message_id`,
  `superseded_by_id`, `bounced_at`, `bounce_code`, `bounce_detail`, `in_reply_to_message_id` (for a
  `REPLY`); status `BOUNCED`; `template_key` nullable for `REPLY` only; the two pending indexes rebuilt
  on `purpose` (§24.2). Pending rows that already break the new rule are superseded by the migration
  (newest kept, a `SENDING` row kept over a newer draft) and each is written to `audit_log`.
- **`email_threads`** (one per addressee, the outbox's exactly-one-addressee rule) and
  **`email_messages`** (inbound and outbound, `message_id`, `in_reply_to`, `reference_ids` —
  `references` is a reserved word — sender, subject, text, sanitised HTML, `outbox_id` when ours,
  `is_bounce`, `handled_at`); **`mail_sync_state`** (folder, `uid_validity`, last UID).
- **`import_rows`** — staged rows: batch, row number and seat index (a wide sheet derives several rows
  from one line), the raw cells, the editable normalised fields, derived party key, issues, the
  existing party it matches and what to do about it, `registration_id` once committed.
  `import_batches` gains `queue_receipts` (§25.3) and statuses `STAGED`, `UNDONE`.
- **`duplicate_candidates`** — an ordered pair, match reasons, status (`OPEN`, `MERGED`, `DISMISSED`).
- **`command_runs`** and **`command_run_items`** (§23.1), with a lease so a continuation and the
  request that started a run never work it at once.
- **`scheduler_heartbeat`** (§27.1) — one row per tick.
- **`show_segments`**: `default_ticket_template_id`, and `auto_approve_clean` (the segment level of
  `review.auto_approve_clean` — the segment level of the cascade reads typed columns only).
  **`segment_message_defaults`**: the default email template per segment per purpose (§24.2).
- **`registration_forms`**: `theme` (banner asset path, colour, override) (§25.6).
- **`user_role`** gains `VIEWER`; the shared admin row becomes a named account (§28) — a data step,
  `R`'s.
- `claim_seats()` and `promote_seats()` keep their signatures; the override's V3 meaning (§23.5) is a
  new body, not a new parameter.
- `schedule_scheduler_jobs()` (§27.2), created everywhere and runnable only where `pg_cron` and
  `pg_net` exist.
- `deleted_at` on every table the Trash lists that lacks one — of those, only `email_templates` did.

**`0201`** (module `Q`) is the one addition since: `audit_log.concert_id` and `command_run_id`, so the
Activity log reads per concert and per run even after the entity is permanently deleted. A
before-insert trigger derives `concert_id` from `entity_type` / `entity_id` for writers that do not
pass it, and existing rows are backfilled.

  hold real guest addresses and registration details. They are rewritten to placeholders, and history

  public tree or is replaced by a fictional example concert.
- **A demo.** A seed script creating a fictional concert end to end, a demo deployment, and a README
  with screenshots. `decisions.md` is the architecture record and stays.
